# 최근 전적 수집·경마장별 평가·구간 비교

2026-10-26 기준 새 작업 흐름입니다. API214_1의 **사이트 전적**과 API155의 **학습 자료**를 따로 수집·기록하고 한 진행표에서 확인합니다. 현재 PC의 인증키·Docker 서비스가 필요합니다. 키는 기존 `scripts/kra.py configure` 설정을 사용합니다.

## 실행

WSL 저장소에서 실행합니다. 화면 코드가 변경됐으므로 최초 한 번 서비스를 재빌드합니다.

```bash
git pull --ff-only origin main
./scripts/up.sh

# 기간·작업 수 확인 (호출·DB 변경 없음)
python3 scripts/kra_sync.py --from 20260726 --to 20261025 --dry-run

# 실제 수집 + 검증된 경주 DB 반영 + 학습 자료 완성 시 비교 평가
python3 scripts/kra_sync.py --from 20260726 --to 20261025 --max-calls 25 --apply --evaluate
```

기간을 생략하면 한국 날짜 기준 최근 3개월~어제가 기본입니다. **여러 날에 걸쳐 재개할 때는 같은 --from/--to를 계속 사용하세요.** 위 기간은 2026-10-26 기준 최근 3개월입니다. `--meets 1`, `--meets 2 3` 등으로 범위를 줄일 수 있습니다. 기본은 세 경마장입니다.

특별 편성일을 빠뜨리지 않도록 지정 기간의 모든 날짜를 확인합니다. 자료 없는 날도 성공한 조회로 기록하므로 재개 시 다시 요청하지 않습니다. 92일×3경마장×2 API이므로 처음에는 빈 날짜를 포함해 최소 수백 회 조회가 필요합니다. 기본 25회씩 나누어 실행하고, 포털 계정의 실제 일일 한도에 맞춰 횟수를 조정하세요. 이 도구가 포털의 잔여 일일 한도를 조회하는 것은 아닙니다.

## 중단·재개·실패

- `--max-calls`는 두 API의 **실제 페이지 요청 합계**입니다. 한 날짜가 2페이지면 2회입니다. 이미 보관된 페이지는 호출 수에 포함되지 않습니다.
- 한도에 도달하면 중단하고 같은 명령으로 이어 받습니다. 페이지 도중 중단돼도 검증된 페이지를 재사용합니다. 여러 프로세스의 동시 실행은 잠금으로 막습니다.
- `--apply`가 없으면 사이트 자료 검증까지만 수행하고 DB에는 쓰지 않습니다. 이후 같은 명령에 `--apply`를 붙이면 저장된 원본을 반영합니다.
- 확인된 코드/비고 쌍인 92/주행중지, 94/경주제외, 95/출전취소는 출주표에 보존하며 정상 완주마와 함께 반영합니다. 미지원 실격·경주불성립·불완전 결과 등은 번호와 이유를 보류 목록에 남깁니다. 같은 날짜의 다른 정상 경주는 반영합니다. 전체 자료가 모두 반영됐다고 간주하지 마세요.
- API/네트워크 오류는 기록하고 실행을 멈춥니다. 해결 후 같은 명령에 `--retry-failed`를 붙이면 실패·보류를 재시도합니다. 성공한 경주는 반복 반영하지 않습니다. 보류 원본은 캐시를 사용하므로 이 옵션이 제공기관 정정 자료를 새로 조회한다는 뜻은 아닙니다.
- 기존 DB 원본과 달라진 결과는 덮어쓰지 않고 실패로 기록합니다. 기존 importer의 원본 지문 검사·트랜잭션을 사용합니다.

```bash
python3 scripts/kra_sync.py --from 20260726 --to 20261025 --status
python3 scripts/kra_sync.py --from 20260726 --to 20261025 --max-calls 25 --apply --evaluate --retry-failed
```

### 마체중 증감이 비어 있는 경우

API가 `488()`을 반환하면 마체중 488kg·증감 미제공으로 저장합니다. `488(0)`의 증감 0kg과 구분하며 원본 표기는 보존합니다. 이 형식 때문에 이전 버전에서 보류된 경주는 업데이트 후 같은 기간의 수집 명령에 `--retry-failed --apply`를 붙여 재처리하세요. 보류 자료는 기존 원본을 사용하고, 이후 새 자료 수집도 호출 한도까지 이어집니다. Python 도구 변경이므로 Docker 재빌드는 필요 없습니다.

### 경주제외·출전취소·주행중지 보류 재처리

이 변경은 V11 `entry.status_note`와 API/화면을 포함하므로 **먼저 서비스를 재빌드**합니다. 기존 자료를 삭제하거나 수집 상태를 초기화하지 마세요.

```bash
git pull --ff-only origin main
./scripts/up.sh
python3 scripts/kra_sync.py --from 20260726 --to 20261025 --max-calls 0 --apply --retry-failed
python3 scripts/kra_sync.py --from 20260726 --to 20261025 --status
```

`--max-calls 0`은 인증키 없이 보관 자료만 재처리하며 API 요청을 하지 않습니다. 보관 자료가 없는 지점에서는 중단합니다. 이미 반영된 경주는 건너뛰고 실패·보류 경주만 재검증합니다. 이 명령에는 `--evaluate`가 없어 모델 평가를 반복하지 않습니다.

92/주행중지는 DNF, 94/경주제외와 95/출전취소는 SCRATCHED로 저장하되 원래 비고를 별도 보존해 화면에서 구분합니다. 착순·결승 시간은 NULL, 구간은 생성하지 않습니다(중간 기록도 원본에는 보존). 경주제외·출전취소마의 배당과 배당 기준 인기는 표시하지 않고 원본만 보존합니다. 일반 완주마의 착순 완전성 검사는 유지합니다. 코드/비고가 맞지 않거나 비완주 코드에 양수 결승 시간이 있으면 보류합니다.

사용자 진단에 남은 `ord=0`, 거리 공란, `98/경주불성립`, 미확인 기수 ID는 임의 변환하지 않습니다. 경주불성립은 일반 완료·출전취소와 구분해야 하므로 현재 자동 반영하지 않습니다. 기수 번호는 실제 값 대신 영문/숫자 형태(A/a/9)를 추가 진단합니다. 이 단계에서 모든 보류가 0이 되는 것은 완료 조건이 아닙니다.

### 추가 확인된 체중 공란·영문 포함 기수 번호

후속 원본에서 `wgHr='()'`가 확인됐습니다. 체중과 증감을 모두 NULL(미제공)로 저장하며 0kg으로 만들지 않습니다. `488()`은 체중 488·증감 미제공, `488(0)`은 체중 488·증감 0으로 계속 구분합니다.

기수 번호 `jkNo`는 기존 숫자 형식 외에 실제 진단으로 확인된 **숫자 2자리 + 영문 대문자 1자리 + 숫자 3자리** 형식도 원문 그대로 보존합니다. 문자에 국적 등의 의미를 부여하지 않습니다. 말/조교사 번호의 허용 규칙은 바꾸지 않았습니다. 기수 프로필 갱신은 영문 포함 ID를 정확히 일치시켜 연결하고, 숫자 ID의 기존 앞자리 0 처리에서는 영문 포함 ID를 제외해 숫자 접두부 충돌을 방지합니다.

이 추가 변경은 Python 도구만 수정하므로 V11이 이미 적용된 환경에서 서비스 재빌드는 필요 없습니다. `git pull --ff-only origin main` 후 위의 `--max-calls 0 --apply --retry-failed` 명령으로 다시 처리하고 `--status`를 확인하세요. 착순 미제공·거리 공란·경주불성립은 여전히 보류하며 새 다운로드를 반복할 필요는 없습니다.

### 조교사 번호가 없는 출주마

`trNo`가 없거나 공란이면 조교사 연결 ID를 NULL로 두고 경주 결과를 반영합니다. 제공된 이름은 보존하되 같은 이름의 기존 조교사에게 자동 연결하지 않습니다. 이름도 없으면 미제공입니다. 0·비숫자·길이 초과 등 공란이 아닌 잘못된 번호는 계속 보류하며 `--status`에 해당 값/형태를 출력합니다.

데이터 재처리는 같은 `--max-calls 0 --apply --retry-failed` 명령을 사용합니다. 이름만 있는 조교사의 화면 표시도 갱신하려면 전체 서비스를 다시 빌드할 필요 없이 아래 명령으로 프론트엔드만 갱신합니다(V11 적용 완료 환경).

```bash
npm --prefix frontend run build
DOCKER_CONFIG="$PWD/.runtime/docker" docker compose up -d --build --no-deps frontend
```

사용자 PC의 최신 결과는 사이트 완료 268/276, 학습 완료 276/276, 보류 8개 날짜×경마장, 누적 API 602회입니다. 보류 58경주는 조교사 번호 검사 2개·착순 미제공 54개·거리 미제공 1개·경주불성립 1개입니다. 조교사 처리 수정의 실제 재반영 결과는 다음 실행에서 확인합니다. 착순·거리 미제공과 경주불성립만 남으면 같은 캐시 재처리를 계속 반복하지 마세요. 정정 원본이나 별도 상태 지원이 필요한 자료입니다.

## 진행표와 저장 위치

`--status`는 실패한 날짜·경마장·단계와 보류 경주번호·사유를 터미널에도 출력합니다. 마체중 표기 오류는 저장된 원본에서 문제가 된 출전번호와 `wgHr` 값도 추려 출력합니다. 상태 조회에는 API 호출이나 DB 변경이 없습니다. 요약의 완료/실패 수는 경주 수가 아니라 날짜×경마장 단위입니다.

착순(`ord`), 기수 식별번호(`jkNo`), 거리(`rcDist`) 오류도 저장 원본에서 검증 불통과 두수와 최대 3두의 문제 값을 표시합니다. 착순은 `ordBigo`(순위 비고)·`rcTime`도 함께 표시해 비완주 표기와 미확정 자료를 조사할 수 있습니다. 짧은 숫자·한글·허용 기호 외 값은 원문을 숨깁니다. 코드 의미를 확인하기 전에는 착순을 임의 변환하거나 문제 말을 제외해 DB에 넣지 않습니다. 이미 수집이 끝난 상태에서 보류가 남으면 반복 다운로드 대신 최신 코드의 `--status` 출력을 먼저 확인하세요.

출력된 `.runtime/kra/sync/20260726-20261025-123.html`을 브라우저에서 열면 날짜·경마장별 **사이트 DB 상태 / 학습 수집 상태 / 실패·보류 이유 / CSV / 평가 상태**를 함께 볼 수 있습니다. 별도 서버는 필요 없습니다. WSL에서 파일 탐색기를 열려면:

```bash
explorer.exe "$(wslpath -w .runtime/kra/sync)"
```

진행표는 마지막 실행 당시의 기록입니다. 다른 PC로 DB를 옮기거나 DB를 초기화한 경우 기존 진행 기록만으로 해당 PC의 DB 반영 여부를 판단하지 마세요. JSON 상태·원본 캐시와 DB를 같은 작업 환경에서 관리합니다. `.runtime`은 Git에 올라가지 않습니다.

## 학습 자료와 평가

각 경마장의 지정 기간 수집이 완료되면 `.runtime/kra/sync/training/`에 CSV를 만듭니다. 기존 `ml/data/seoul-2025.csv`와 서비스 모델을 덮어쓰지 않습니다. 전체 날짜를 수집했어도 학습 계약에 맞지 않는 동착·불완전 경주 등은 CSV에서 제외됩니다.

`--evaluate`는 요청한 경마장의 CSV가 모두 준비된 후 아래 세 실험을 실행합니다.

| 실험 | 학습 대상 | 평가 출력 |
|---|---|---|
| seoul | 서울 | 서울 홀드아웃 |
| seoul_busan | 서울+부산경남 | 동일 날짜 기준의 서울·부산경남 결과 각각 |
| jeju | 제주 | 제주 홀드아웃 |

전체 날짜의 앞 80%/뒤 20%를 나누는 공통 경계일을 사용합니다. 서울 단독과 서울+부산 모델은 **같은 서울 검증 경주**에서 비교합니다. 각 실험에 학습일 20일·검증일 5일 이상이 필요하고, 전체로는 서로 다른 경주일 30일 이상이 필요합니다. 부족한 자료는 `missing_tracks`/`insufficient_dates`로 기록하며 점수를 만들어 내지 않습니다.

시장 정보 없는 고정 RandomForest를 사용하며 모델 점수는 승률이 아닙니다. 시장 기준선은 모든 출주마의 배당이 있는 경주만 평가하고 해당 경주에 대한 모델 지표도 별도로 제공합니다. 보고서의 `marketRaces`, `modelOnMarketSubset`을 함께 확인하세요. 단일 시간순 분할 결과이고 인물은 이름으로 연결하므로 동명이인 등의 한계가 있습니다.

별도 평가 명령:

```bash
.runtime/ml-venv/bin/python ml/evaluate_tracks.py \
  .runtime/kra/sync/training/1-20260726-20261025.csv \
  .runtime/kra/sync/training/2-20260726-20261025.csv \
  .runtime/kra/sync/training/3-20260726-20261025.csv \
  --output .runtime/kra/track-evaluation.json
```

평가는 **서비스 모델을 자동 교체하지 않습니다.** 클라우드에서는 저장소의 서울 2025 CSV로 서울 평가만 직접 재현했습니다. 2026-10-26 사용자 PC 출력에서는 20260726~20261025 학습 수집 276/276과 서울+부산·제주 평가 완료를 확인했습니다. 서울 단독은 `insufficient_dates`이고, 통합 모델의 서울/부산 및 제주 AUC는 각각 0.660/0.759/0.651로 해당 시장 기준선보다 낮았습니다. 이는 사용자 제공 실행 결과이며 클라우드에서 해당 CSV나 평가 JSON을 직접 검증한 결과는 아닙니다. 평가 보고서 확인 후 별도 기간의 검증과 서비스 모델 적용 범위를 결정합니다.

## 화면

- 경주 상세의 구간 기록 아래에서 최대 4두를 선택해 순위 그래프·초반 순위·착순·순위 변화·마지막 600m·경주별 스타일을 비교합니다.
- 마지막 600m 빠른순 정렬이 가능하며 기록 없는 말은 뒤에 표시합니다. 누락된 시간이나 순위는 0으로 채우지 않습니다.
- 배당의 출처와 시각이 같으면 표 위에 한 번만 표시합니다. 자료별 출처·시각이 다르거나 말의 여러 경주 전적을 보는 경우에는 각 행에 표시합니다.
- 경주 상세에서 `미제공`인 주로는 `주로 정보 미제공`으로 표시합니다. 인쇄 시 출주표의 글자·여백을 줄여 넓은 표의 잘림을 완화했습니다.
