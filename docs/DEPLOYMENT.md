# 배포와 운영 준비
현재 Compose는 단일 Linux 개발/시연 환경용입니다. 외부 운영 서버에 실제 배포하지 않았으며 비용이나 HTTPS 설정 완료를 주장하지 않습니다.

- 서버: Docker/Compose를 지원하는 Linux VM, 초기 권장 2~4 vCPU/4GB 이상 RAM/20GB 이상 디스크. 실제 용량은 데이터/트래픽에 따라 측정하세요. 클라우드 VM·디스크·백업·도메인·트래픽 비용이 발생합니다. 요금은 공급자와 리전에 따라 다르므로 배포 시 견적을 확인합니다.
- 외부 공개는 reverse proxy(Caddy/Nginx 등)의 HTTPS 443으로만 하고 프론트 포트로 전달합니다. DB/API/ML 직접 외부 공개를 피합니다. 현재 loopback 바인딩을 무분별하게 0.0.0.0으로 바꾸지 않습니다.
- 운영 JWT_SECRET은 암호학적으로 안전한 최소 32바이트 키, DB 비밀번호는 운영 비밀 관리 도구에서 주입합니다. `.env` 예시의 빈 문자열을 그대로 사용하지 않습니다. 토큰 키 교체 시 기존 세션은 무효화됩니다. proxy placeholder 기반 비밀값은 로컬 DB/암호 연산용 원시 키를 대체할 수 없습니다.
- MySQL 볼륨은 `keiba_mysql_data`이며 VM 디스크/볼륨의 보존 및 암호화를 설정합니다. 정기적인 mysqldump 또는 스토리지 백업과 실제 복구 테스트가 필요합니다. 환경 스냅샷이 Docker named volume을 보존한다고 가정하지 않습니다.
- Flyway는 시작 시 순서대로 migration을 적용합니다. 적용된 migration을 수정하지 말고 새 버전을 추가하세요. 운영 변경 전 백업을 준비합니다.
- 실제 서비스에서는 추가적인 남용 방어, 이메일 인증/복구, 관측성/경보, 비밀 회전, 토큰 철회 테이블 만료 레코드 정리를 추가 검토합니다. 현재 SRS 범위에는 포함되지 않습니다.
- 이미지 태그를 배포 시 digest로 고정하고 취약점 검사/정기 업그레이드 정책을 운영하세요. 테스트된 프로젝트 의존성은 Gradle 및 npm/Python lockfile에서 확인합니다.
- 브라우저 CSP 및 nosniff 헤더를 Nginx에서 제공하며 API CORS는 같은 출처 프록시 흐름을 전제로 합니다. JWT는 Bearer 헤더에만 사용하고 쿠키 세션을 사용하지 않아 이 API에는 CSRF를 비활성화했습니다. HTTPS는 배포 reverse proxy에서 종단합니다.
- 새 클라우드 task의 컨테이너/볼륨 복구는 별도로 검증해야 합니다. 코드만 있는 새 머신에서는 `scripts/up.sh`로 이미지와 가상 샘플 DB를 재구축할 수 있습니다. 회원/즐겨찾기 보존은 별도 DB 백업 복원이 필요합니다.

## 준비된 HTTPS 구성
서버와 도메인은 아직 없습니다. 아래 명령은 해당 자원을 준비한 **새 운영 서버**에서 실행하는 절차이며 현재 외부 배포 완료를 뜻하지 않습니다.

1. Linux VM에 Docker/Compose 2.24.4 이상을 설치하고 저장소를 복제합니다. DNS A/AAAA를 서버로 연결하고 방화벽은 웹 80/443과 제한된 관리 접속만 허용합니다.
2. `scripts/init-env.py`로 초기 파일을 만들고 운영 비밀 관리 방식으로 `.env` 값을 보관합니다. 기존 DB의 비밀번호를 임의로 바꾸지 않습니다. `.env`에 실제 `DOMAIN`과 `ACME_EMAIL`을 추가합니다.
3. `./scripts/build.sh`와 `docker compose -f compose.yaml -f compose.production.yaml build`를 실행합니다.
4. `docker compose -f compose.yaml -f compose.production.yaml up -d`를 실행합니다. Caddy가 공개 인증서를 요청하고 자동 갱신합니다. 운영 관리 명령에도 반드시 두 Compose 파일을 사용합니다.
5. 공개 도메인의 인증서/리다이렉트, 회원가입/로그인/즐겨찾기/예측, 서버 재시작, 외부 모니터링과 별도 서버 복구를 검증합니다. 운영 환경에서 테스트 데이터 생성 스크립트를 실행하지 않습니다.

운영 override는 기본 DB/API/ML/프론트 포트 매핑을 제거하고 gateway의 80/443만 공개합니다. Caddy 인증서 볼륨은 유지해야 합니다. 기본 프론트는 로그인/가입에 IP별 분당 5건, 초기 burst 10건을 허용하며 초과 시 한국어 429를 반환합니다. 공유 IP 사용자가 많은 환경에서는 실제 트래픽을 보고 조정하세요. 프론트는 전용 Docker 네트워크의 사설 IP 프록시를 신뢰합니다. 공유 네트워크/CDN/로드밸런서를 추가하면 `set_real_ip_from`과 Caddy trusted proxy 설정을 해당 신뢰 경계에 맞게 제한해야 합니다. 직접 API 포트를 공개하면 프록시 제한을 우회하므로 운영 override를 유지합니다.

`python3 tests/check_tls.py`는 별도 임시 Caddy와 로컬 CA로 인증서·호스트명 검증을 유지한 HTTPS 전달을 검사합니다. 공개 ACME 검증이나 실제 도메인 배포를 대체하지 않습니다.

## 백업 및 복구 검사

KRA 원본·학습 CSV·수집 진행표와 DB를 함께 보관하려면 [통합 백업 안내](KRA_BACKUP.md)의 `python3 scripts/kra_backup.py create`를 사용하세요. 아래 명령은 DB만 백업합니다.
개발/점검 환경에서 다음을 실행합니다.

```bash
python3 scripts/backup.py
```

`mysqldump --single-transaction`으로 `.runtime/backups/`에 gzip SQL(0600)을 만들고, 무작위 이름의 별도 MySQL 스키마에 복원합니다. 모든 테이블의 행 수와 논리 체크섬을 원본과 비교한 뒤 임시 스키마만 삭제합니다. 원본 DB를 덮어쓰지 않습니다. 검사 중 쓰기가 발생하면 일치 확인에 실패할 수 있으므로 조용한 시간에 실행하세요. 성공 JSON 보고서를 확인한 백업만 사용합니다. 중간 실패 파일은 검증된 백업으로 취급하지 않습니다.

백업에는 회원 정보와 비밀번호 해시가 포함됩니다. Git에 올리지 않고 접근을 제한하며 운영에서는 암호화된 별도 저장소로 복사하고 보존 기간·자동 스케줄·실패 알림을 설정합니다. 같은 서버의 임시 스키마 복원은 서버 전체 손실 대비 검증이 아닙니다. 새 서버에서 동일 MySQL 버전으로 **빈 전용 DB**에 복원하고, JWT 키 및 애플리케이션 설정을 복구한 뒤 로그인/즐겨찾기/철회 토큰을 확인해야 합니다. 실제 서버 확보 후 이 절차를 검증하고 복구 목표 시간과 허용 데이터 손실을 정합니다.
