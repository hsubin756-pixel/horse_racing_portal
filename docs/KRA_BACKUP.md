# DB와 KRA 수집 자료 통합 백업

## 실행

수집·DB 반영·관리자 수정 등 쓰기 작업을 멈춘 뒤 WSL 저장소에서 실행합니다. Docker DB 컨테이너는 켜져 있어야 합니다. 서비스 재빌드나 API 호출은 필요 없습니다.

```bash
git pull --ff-only origin main
python3 scripts/kra_backup.py create
```

`백업 완료: ...tar.gz`와 `DB 별도 스키마 복원·파일 SHA-256 검사 통과`가 출력되면 성공입니다. 기본 위치는 `.runtime/backups/kra/`, 파일명은 UTC 시각과 임의 식별자입니다. 다른 위치는 `create --directory 경로`로 지정하되 `.runtime/kra` 내부는 허용하지 않습니다.

```bash
explorer.exe "$(wslpath -w .runtime/backups/kra)"
```

위 명령으로 폴더를 열어 `.tar.gz`를 USB 등 별도 저장장치에 복사하세요. 같은 PC에만 남겨두면 디스크 손실에 대비할 수 없습니다. **백업은 암호화되지 않았고 회원 정보·비밀번호 해시가 포함될 수 있습니다.** Git·공개 링크·이 대화에 올리지 마세요. 외부 보관에는 암호화된 저장장치를 권장합니다. Windows로 복사하면 Linux 접근 권한이 그대로 보장되지는 않습니다.

## 포함 내용

| 경로 | 내용 |
|---|---|
| `database/backup.sql.gz` | 현재 keiba DB 전체: 경주·말·회원·메모·관심 기록·DB 내 원본 등 |
| `database/report.json` | 임시 스키마 복원 검사 기록, 테이블별 행 수·체크섬 |
| `kra/` | `.runtime/kra`의 API 원본·페이지 캐시·API155 자료·CSV·진행 JSON/HTML·평가 보고서 |
| `manifest.json` | 파일별 크기·SHA-256, 원래 프로젝트 경로, Git 커밋, 생성 시각 |

`.env`, `.runtime/kra/service-key`, 잠금 파일은 제외합니다. Git 저장소·Docker 이미지·전체 `.runtime`·모델 실행 환경도 포함하지 않습니다. 설정/인증키는 별도로 안전하게 보관하거나 복구 시 다시 설정해야 합니다.

기존 `backup.py`로 DB를 백업하고 같은 MySQL 서버의 `restore_check_*` 임시 스키마에 복원해 테이블을 비교한 뒤 임시 스키마를 삭제합니다. 운영 DB를 덮어쓰거나 서비스를 중지하지 않습니다. UTF-8 문자셋을 명시합니다. 묶음 생성 후에도 KRA 원본과 DB 변경 여부를 확인합니다. 실패 시 완성 파일을 게시하지 않고 작업용 파일을 정리합니다. 이전 성공 백업은 자동 삭제하지 않습니다.

실행 중인 `kra_sync.py`와 잠금으로 충돌을 막습니다. 다른 도구와 웹 요청까지 잠그지는 않으므로 백업 중 쓰기 작업을 피하세요. 임시 DB와 압축 파일을 만들 여유 디스크 공간이 필요합니다. 실패 원인을 해결한 뒤 재실행하고 완료 메시지가 없는 파일은 사용하지 마세요.

## 복사 후 검사·별도 폴더에서 확인

아래 경로는 실제 백업 파일 경로로 바꿉니다.

```bash
python3 scripts/kra_backup.py verify /백업/저장위치/백업파일.tar.gz
python3 scripts/kra_backup.py extract /백업/저장위치/백업파일.tar.gz --to .runtime/recovery-preview
```

`verify`는 DB/API 연결 없이 파일 목록·경로·크기·SHA-256과 생성 당시의 DB 복원 검사 기록을 확인합니다. DB 재복원은 수행하지 않습니다. 내부 해시는 백업 출처의 진위를 인증하지 않으므로 본인이 생성·보관한 백업에 사용하세요.

`extract` 대상 폴더는 존재하지 않아야 합니다. 기존 폴더는 덮어쓰지 않으며 경로 탈출·링크·중복 파일·해시 불일치를 거부합니다. 새 폴더에 풀기만 하고 운영 DB나 `.runtime/kra`를 자동 교체하지 않습니다.

## 실제 장애 복구 시 주의점

먼저 별도 환경의 빈 DB에 복원한 뒤 회원·경주·메모·원본·진행 기록의 일치를 확인해야 합니다. **진행 JSON에는 기존 프로젝트의 절대 경로가 있을 수 있습니다.** 다른 PC/경로에서는 `tasks.*.archive`, `exports.*.path`, `evaluation` 등 기존 루트의 경로를 새 루트로 조정하고 상태 조회를 확인하세요. DB와 진행 기록은 같은 백업 묶음으로 복구합니다. 완료 진행표만 복구한 뒤 빈 DB에서 수집을 재개하면 필요한 경주를 건너뛸 수 있습니다.

현재 직접 검증 범위는 같은 서버의 임시 스키마 DB 복원과 새 폴더 추출입니다. 다른 PC·서버 전체 손실 상황의 복구 완료를 의미하지 않습니다. 운영 DB 교체를 자동 수행하는 명령은 제공하지 않습니다.
